# Метрика умного поиска

Цифры для питча (слайд «Было → стало») и для выбора запросов на сцену.

## Итог для питча

- **Правильный волонтёр в топ-3 — в 10 из 10 запросов** (YandexGPT, 40 вымышленных анкет, каждый запрос прогнан дважды — 20 из 20).
- **Из 24 «правильных» людей в тройку попадают 23.**
- **Ответ — 5–8 секунд** вместо ручного поиска по таблице.
- **Без AI поиск тоже работает:** модель недоступна — те же 10 из 10 по смыслу анкеты, но без фильтра по времени и объяснений.

## Как меряем

- 10 эталонных запросов координатора — `data/demo/search_benchmark.json`. У каждого заранее отмечены 2–3 «правильных» волонтёра из 40 вымышленных анкет (`data/demo/volunteers.json`) и почему именно они.
- **hit@3** — в первой тройке есть хоть один правильный. Главная цифра для жюри.
- **Нашли из ждали** — строже: сколько правильных вообще попало в тройку (24 на прогон).
- **Без AI** — ответы, где LLM не участвовала (недоступна или заглушка `fake`), поиск шёл по векторам и словам.
- **Время** — от запроса до ответа бэкенда, среднее; на проде — без обрывов связи по пути до сервера.

Повторить локально: `make dev` → `make seed` на пустой базе → `make benchmark`.
На проде: `BACKEND_URL=https://deti.201-34-157-90.sslip.io/api uv run python scripts/benchmark.py --repeat 2`.

## Что это значит — честно

- **С YandexGPT поиск точнее, чем без неё**, и это видно там, где важно время: в запросе 5 («будни днём») без AI в тройку попадал человек, свободный только вечером и в выходные; с LLM фильтр по времени его убирает.
- **Без LLM поиск не ломается**: 10/10 по смыслу анкеты. Но на демо-анкетах те же слова, что в запросах, — на живых анкетах разрыв с LLM будет больше.
- **Куда уходит время.** Разбор запроса — 1–3 с, переранжирование с объяснением — 4–7 с (модель пишет оценку и фразу для каждого из 10 кандидатов; разброс — от нагрузки на Yandex). Lite быстрее всего на 2 с и заметно хуже. Дальше ускорять — показывать кандидатов по векторам сразу и дописывать оценки, когда придут (интерфейс), или потоковый ответ.
- **Если модель поймёт запрос слишком узко** (так было на Lite) и жёсткий фильтр отсечёт всех, поиск ослабляет условия — сначала время, потом регион — и пишет об этом в «Как я понял запрос»: «Никого не нашлось в это время — показываю без этого условия» (T-72). Пустой список придёт, только если подходящих нет совсем.

## Запросы для сцены

На YandexGPT Pro каждый прогнан дважды на проде — топ одинаковый.

1. **«Нужен фотограф на четверг утром, разово»** — запрос из питча. Чипсы: «фото · будни утро · разово». Топ: три фотографа с предметной съёмкой (90, 85, 80), причины вроде «Предметная съёмка, обработка фото, своя камера». ~8 с.
2. **«Кто может в субботу помочь на инклюзивной мастерской по керамике?»** — 3 из 3 керамистов, свободных в выходные; «Важно: инклюзивная мастерская». ~7 с.
3. **«Во Владикавказе в субботу нужен волонтёр на кулинарный мастер-класс»** — 3 из 3, регион «Северная Осетия», из 40 анкет проверено 4. ~5 с.

Запрос вне данных: **«нужен водолаз в Осетии ночью»** — у всех оценка 0 и причина «Навыки в кулинарии, не водолаз»: система честно показывает, что подходящих нет.

Подбор под возможность «Фотосъёмка изделий для каталога» (кнопка «Подобрать») — первым фотограф с предметной съёмкой (90), дальше — те, у кого опыта меньше (60, 35).

Перед выступлением — прогнать эти запросы ещё раз по `docs/DEMO_CHECKLIST.md`: 5–8 секунд на сцене ощущаются долго, пока идёт поиск, стоит сказать фразу из сценария.

## Как переключить модель

- Прод: переменная репозитория `LLM_PROVIDER=yandex`, секреты `YANDEX_API_KEY` и `YANDEX_FOLDER_ID`; модель — переменная `YANDEX_MODEL` (по умолчанию `yandexgpt/latest`). После изменения — запустить workflow Deploy.
- Эмбеддинги меняются вместе с провайдером: анкеты, засеянные на других эмбеддингах, поиск по смыслу не увидит — базу нужно засеять заново.
- Локально: те же переменные в `.env` (шаблон — `.env.example`).
